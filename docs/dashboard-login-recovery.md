# Recovering the dashboard login through owner SSH access

23 October 2026. Prepared and fixture-tested; no live password or 2FA reset
has been performed by the agent. This is an explicit owner recovery action,
separate from normal package installation and from factory reset.

The existing node has an Argon2id dashboard password and TOTP enrolment.
The provided temporary login input was rejected before reaching the TOTP
challenge, and the owner reports having the authenticator code only.
The rejected temporary input was removed after use. Credentials and 2FA
codes were not printed or included in repository evidence.

The source stores the TOTP secret encrypted under a key derived from the
password (`core/archipelago/src/totp.rs`, `decrypt_secret` and `rekey`).
A current six-digit code cannot re-encrypt that secret for a new password.
The prepared reset therefore replaces the password and clears the old
TOTP enrolment. The owner must enrol 2FA again after logging in. It also
signs out browsers and revokes paired-device tokens; devices need pairing
again. SSH authentication is preserved.

## Owner command

The helper is staged in the node's private install bundle. Run from the
owner's terminal, using the already-authorised SSH key:

```bash
ssh -t root@<node> 'python3 /root/archy-spry-qualification/reset-dashboard-login.py'
```

Enter and confirm a new dashboard password when prompted. Input is hidden,
never passed in process arguments and never written as plaintext to a file.
The helper requires at least 12 characters with uppercase, lowercase, a
digit and a special character, matching the existing dashboard policy.
It explains the effects and requires the exact confirmation:

```text
RESET LOGIN AND RE-ENROL 2FA
```

Cancelling or a password mismatch changes nothing. The agent has not run
this interactive command or accepted that confirmation for the owner.

After confirmation the helper briefly stops the Archy backend, takes a
private root-only backup under `/root/archy-login-backup-<UTC timestamp>/`,
then updates only these authentication files:

- `user.json`: replace the password hash and clear old TOTP; preserve role,
  onboarding state and unknown fields.
- `sessions.json` and `device-tokens.json`: clear old login authorisations.
- `remember_secret`: replace the remember-me/CSRF signing secret, invalidating
  old persistent browser login cookies.

The backup is completed before atomic writes. A changed account or symlink
is refused; a partial write failure restores the original authentication
files. The backend is restarted in a `finally` block. Active application
containers are not stopped. Node identity, wallet and application files,
firewall rules, operating-system passwords and SSH keys are not modified.
This is not a forensic-erasure claim for previous passwords or sessions.

An existing encrypted recovery-phrase backup, if present, is left untouched
and still requires its original passphrase. The examined qualification node
has no `identity/master_seed.enc`; resetting its login cannot create or
recover a missing recovery-phrase backup. The node's existing key files are
not regenerated by this procedure.

Once complete, sign in through the existing SSH tunnel, save the new password
in a password manager, re-enrol 2FA and save the newly issued backup codes.
The original 2FA entry should only be retired after the new enrolment works.
Do not delete the root-only authentication snapshot until the owner accepts
the result. Restoring old authentication also restores its old credentials
and grants, so it is an explicit owner recovery decision.

## Evidence and remaining gates

The [receipt](evidence/archy-login-recovery-20261023.json) records five
recovery tests on macOS and on the actual Linux node: key/role preservation,
private backups, stale-input refusal, symlink refusal and partial-write
rollback. Synthetic Argon2 generation/verification on the node matches the
reviewed Rust parameters (Argon2id v19, memory 65536, time 3, parallelism 4).
The Debian `python3-argon2` package and its small library dependency were
installed to run the helper; no live credential was changed during setup.
The dependencies and helper are retained for the owner to perform recovery.

The [Spry installer](../node/install-spry-lab.py) now supports
`--interactive-login`. It follows the normal password-then-TOTP API flow,
refuses a partial session before installing anything, accepts a six-digit
code only, and verifies full authentication before mutation. Ten installer
boundary tests pass. Its original non-interactive file mode remains available
when the server does not demand a TOTP challenge. Neither route bypasses 2FA.

Actual recovery, fresh dashboard login and re-enrolment remain owner steps.
Spry has still not been installed through the dashboard API, no public TURN
ports were opened and no service discovery was published by this increment.
